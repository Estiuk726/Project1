# ADR 0002: Database hosting on Supabase, EU (Frankfurt)

- Status: Accepted
- Date: 2026-09-27
- Decides: PRD Section 22, D4 (hosting and database region, database part)

## Context

PRD 14.1 asks for managed PostgreSQL in an EU region. Users are in South Asia and Europe, and PRD 11 requires EU hosting where available. Supabase was the named candidate.

## Decision

- Production and staging Postgres run on **Supabase**, region **Frankfurt (eu-central-1)**.
- The app talks to Postgres through **Drizzle ORM** in `packages/db` with the `postgres` (postgres.js) driver. Nothing outside `packages/db` imports Supabase or driver types.
- Schema changes are SQL migrations in `packages/db/migrations`, generated by drizzle-kit and applied by `pnpm db:migrate`. The Supabase dashboard is never used to change the schema.
- Every table in the `public` schema has **row level security enabled with no policies**. Supabase exposes `public` through its Data API; with RLS on and no policies, that API returns nothing. The app connects as the table owner, which bypasses RLS, and enforces authorization in the domain layer (CLAUDE.md).
- Connections: migrations use the direct or session-pooler connection string; the app uses the transaction pooler (port 6543) with prepared statements disabled.
- CI and local tests use plain Postgres (17 in CI), not a Supabase project.

## Consequences

- One provider can later also cover auth (D3), storage and realtime (D5), but those are separate decisions with their own ADRs.
- Supabase-specific features (Data API, RLS policies, database functions called from the client) are not used; switching to another Postgres host means changing connection strings only.
- A table added without `ENABLE ROW LEVEL SECURITY` would be readable through the Supabase Data API. A test checks that every `public` table has RLS enabled.
